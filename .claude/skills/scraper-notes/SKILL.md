## Concurrency

- **`MAX_CONCURRENT_GROUPS > 1` (default, 6)**: groups scan in parallel via `ThreadPoolExecutor(max_workers=MAX_CONCURRENT_GROUPS)`. Each worker thread (`_scan_group`) launches its *own* `browser`+`context` (cookies injected from `storage_state_path`, exported once from the login phase) — multiple simultaneous browser instances from one FB account, higher checkpoint/ban risk than the real profile's own fingerprint.
- **`MAX_CONCURRENT_GROUPS == 1`**: true sequential mode. `run_scraper()` never exports `storage_state` or closes the login `context` early — it scans every group one at a time, on the same `page`, inside the original `launch_persistent_context()` session (`chrome_profile/`), with a randomized 5–15s pause between groups. Lowest checkpoint risk since nothing ever diverges from the real profile.
- Both modes share the actual per-group scanning logic via `_scan_group_page(page, target_url, group_label, sheet, seen_urls, headless, live)` — `_scan_group` (parallel) wraps it with browser/context lifecycle; the sequential loop in `run_scraper()` calls it directly. Keep this function as the single place per-post logic lives; don't duplicate it into either caller. It delegates to `_scroll_and_harvest()` (scroll loop + early-stop; the streak rule itself is the pure, unit-tested `_update_old_streak()`) and `_collect_valid_posts()` (all the no-LLM gates: cached verdict, sheet-seen, scan cutoff, `_content_prefilter`, text-dedup), so each can be changed without reading the whole 100+ line scan body.
- Shared state guarded by module-level locks, now spread across the modules that own each piece of state: `_sheet_lock`/`_print_lock` (`core/util.py` — `_sheet_lock` covers both `seen_urls` reads/writes and `sheet.append_row`, kept together to avoid duplicate-URL races; `_print_lock` via `_safe_print` prevents interleaved terminal output), `_gemini_lock` (`core/llm.py`, guards `GEMINI_EXHAUSTED`/`GEMINI_ERROR_COUNT`), `_gmaps_cap_lock` (`integrations/maps.py`, guards the one-time over-cap notice print), `_text_dedup_lock`/`_headless_checkpoint_hit` (`sources/fb_scraper.py`). `core/storage.py` has its own internal lock for all SQLite access (both `posts` and `api_usage`), so the Maps-usage counter is safe to increment from every group thread.
- Checkpoint/CAPTCHA on any tab (headful mode): `_checkpoint_lock` + `_resume_event` elect one thread as "leader" to prompt once; other threads block on the event, then all retry navigation once resolved (`_handle_checkpoint_if_present`). Headless mode instead uses `_checkpoint_lock` to guard `_headless_checkpoint_hit`, a one-shot flag that makes every other group abort immediately (see Anti-Bot section); the sequential loop also breaks out early on a headless checkpoint, marking the remaining un-scanned groups as checkpoint-skipped too.
- Raising `MAX_CONCURRENT_GROUPS` speeds up a run but increases simultaneous requests from one FB account — real risk of triggering a checkpoint faster; `1` is the safe fallback
## Anti-Bot / FB Fragility

- CAPTCHA/checkpoint loop (`_handle_checkpoint_if_present`) requires human intervention in headful mode — cannot be automated away; pauses all parallel tabs, not just the one that hit it. In `--headless` mode there's no window to solve it in, so instead: a screenshot (`checkpoint_<group_label>.png`) is saved, `_headless_checkpoint_hit` is flagged so other groups skip immediately instead of each hitting the same wall, and `_scan_group_page` returns `{"checkpoint_hit": True, ...}` for that group via `HeadlessCheckpointAbort` — the run finishes normally and prints "N group(s) skipped due to a security checkpoint — rerun headful" instead of hanging forever on `input()`
- Both Chromium launches (`_scan_group`'s per-thread browser and `run_scraper`'s persistent login context) pass `--autoplay-policy=user-gesture-required` — Chrome autoplays muted videos by default, and Facebook's feed has video posts that would otherwise start playing on scroll, wasting bandwidth/CPU during a scan
- Both launches use Playwright's bundled Chromium (no `channel="chrome"`) — cross-platform (Windows/Linux/ARM64), no separate real-Chrome install step. `_CHROME_LAUNCH_ARGS` (`sources/browser.py`) adds `--no-sandbox --disable-gpu` on Linux only (`sys.platform.startswith("linux")`): verified 2026-07-18 that without them, Chrome's sandbox can fail to initialize in some Linux VM environments, hanging `page.goto()` past its timeout on every navigation rather than erroring — a bare `google-chrome --no-sandbox --disable-gpu` CLI call loaded facebook.com in 11s on the same box where Playwright's launch (missing these flags) hung indefinitely. Windows keeps the original anti-detection args unchanged.
- **Both contexts use an explicit `viewport={"width": 1366, "height": 1600}`, not `no_viewport=True`.** Verified 2026-07-18: in headless mode, `no_viewport=True` leaves Chromium at its tiny default window (~784×505), which collapses Facebook's layout and breaks scroll almost immediately — `window.scrollY` gets stuck after one wheel tick and the group feed never grows past the ~4 posts that load on initial paint. This was the root cause of suspiciously low per-group post counts (avg ~5-6/group despite `SCROLL_COUNT=20`). Headful runs never showed it because a real on-screen window is already large. Don't revert to `no_viewport=True`.
- **Scroll early-stop counts already-processed posts**, not just ones older than the cutoff (`_scan_group_page`): a post for which `storage.should_skip()` is true adds to the `consecutive_old` streak like an old-dated one. Without this, a group with no saved `last_scan_time` can't reach the `MAX_POST_AGE_DAYS` cutoff in `FIRST_SCAN_SCROLL_COUNT` scrolls, never sets `caught_up`, never saves a baseline, and re-crawls the same ~80 scrolls every run (seen 2026-10-15: 23 of 33 groups).
- **Per-group scroll cap scaled by yield** (`_yield_scaled_scroll_cap()`, 2026-11-07, idea from bgu-housing-bot): once a group has a saved baseline and `GROUP_YIELD_MIN_HISTORY` (300) posts in the DB, its `SCROLL_COUNT` cap scales with its added/total rate — `GROUP_YIELD_MIN_SCROLLS` (8) at ≤`GROUP_YIELD_POOR_RATE` (0.2%), full at ≥`GROUP_YIELD_RICH_RATE` (1%), linear between. Cut the summed cap 990 → 798 across the 33 groups when added. Never applies to the first-scan backfill. Kill switch `GROUP_YIELD_SCALING`.
- **Dead-link check** (`_prune_dead_links()`, `PRUNE_DEAD_LINKS_ENABLED`): right after login, before any group, it visits every URL already in the main sheet tab and removes rows whose post Facebook now shows as unavailable (`_is_post_removed`, `_DEAD_POST_RE`); a dry run only reports. Each visit plus its 2–5s pause takes ~8.5s, so a 60-row sheet is ~8 minutes — it prints the listing count with a time estimate up front and progress every `_DEAD_LINK_PROGRESS_EVERY` (10) listings (2026-11-12; before that it was silent and a run looked stuck after "Opening Facebook..."). Facebook URLs only: the Yad2 tab isn't visited. DB rows are untouched.
- URL order shuffled via `random.sample` each run
- **Progress bars** (`_ScanProgress`, 2026-11-12): created by `run_scraper()` around either scan loop (`progress=` param; `None` = no bar, as in the tests that don't pass one). After each finished or crashed group, and every `PROGRESS_TICK_S` (30) from a daemon ticker thread, it prints a console line (`[####----] 23/54 groups | 4 added | 12 min elapsed | ~15 min left` — a line per report, not a `` redraw: parallel groups print at once and the console is teed to the log) and, on a live run with Telegram, edits the run-started message via `telegram_notifier.update_run_progress()`. Time left (`_estimate_seconds_left`) = average time per finished group × total − elapsed, so it counts down between finished groups and corrects at each one; `None` until the first group finishes. An identical report is skipped (Telegram rejects an edit that changes nothing). Covers the group scan only, not the dead-link check before it.
- Per-post pacing comes from the Gemini rate lock (4s minimum between LLM calls) plus the jittered scroll delays — there is no per-post `time.sleep` anymore
- Scroll distance jittered too, not just the delay: `page.mouse.wheel(0, random.randint(3000, 5000))` — a fixed pixel distance every scroll is as bot-like a signal as a fixed delay. The scroll loop also does an occasional (~25% of iterations) `page.mouse.move(..., steps=5-15)` cursor drift — a human's mouse doesn't sit frozen while reading a feed
- **Stealth patches** (added 2026-07-18, inspired by hyuwowo/fb-marketplace-scraper): `_apply_stealth(page)` runs `tf-playwright-stealth`'s `stealth_sync` on every page (both launch sites), before first navigation. Kill switch: `STEALTH_ENABLED` in config.py. Two patches are deliberately disabled via `StealthConfig(navigator_user_agent=False, navigator_languages=False)` — the package fakes them with a hardcoded Chrome 95 UA and en-US (verified against v1.2.0), which would be a louder bot signal in 2026 than what it hides and would stomp the real-profile fingerprint below. If the package is missing, the bot warns once and runs without it.
- **Headless fingerprint parity audit** (2026-10-15, `bot.sannysoft.com` self-test + comparison against this machine's headful Chromium): the old headless session passed every sannysoft row but still differed from the headful session the account logged in with — WebGL was a *random* Mac/mobile GPU per run (tf-playwright-stealth's spoof, clashing with the Windows UA; without it, headless shows SwiftShader), the UA carried the full build (`149.0.7827.55`) where real Chrome sends the reduced `149.0.0.0`, and `navigator.languages` was `["en-GB"]` vs headful `["en-US","en"]`. Fixed in `sources/browser.py`/`config.py`: `_normalize_user_agent()` (strips `HeadlessChrome`, applies UA reduction; used by both the probe launch and the worker UA export), `BROWSER_LOCALE` (`en-US`, passed as `locale=` to the persistent context so Accept-Language/`navigator.language` match; workers inherit it via the exported `real_locale`), `WEBGL_VENDOR`/`WEBGL_RENDERER` (machine-specific, set in gitignored `config_local.py` from a headful `UNMASKED_*` read; `None` = no WebGL spoof, never the random one) applied by an own `getParameter` init script, and `navigator.languages` set from `BROWSER_LOCALE` by an own init script. The stealth package's `webgl_vendor` *and* `navigator_languages` patches are both disabled: its languages patch ignores `StealthConfig.languages` and uses a randomly generated Accept-Language (seen: `["en-IO","*"]`). Re-run the self-test after upgrading Playwright/the stealth package or changing GPU/drivers. Known residual: `navigator.plugins.length` is 3 (stealth's spoof) vs 5 headful.
- **Fingerprint consistency**: parallel workers get the login profile's real UA (`navigator.userAgent`, captured before `storage_state` export, "HeadlessChrome" stripped) and `navigator.language` passed into `new_context(user_agent=..., locale=...)` — otherwise the same account presents Playwright's default fingerprint on worker "devices" alongside the real one. Headless sequential mode: `launch_persistent_context` gets a corrected UA from a throwaway probe launch, since headless Chromium's UA literally says "HeadlessChrome" (HTTP header + JS) and a UA can only be set at context creation. `browserforge`-style *random* fingerprints were considered and rejected — a random identity per session diverges from the account's known device, more suspicious for a logged-in single-account scraper, not less.
- **Post text is read from the body container, not the whole article** (`_read_post_text()`, 2026-11-07, selectors from MasuRii/FBScrapeIdeas): the joined text of `div[data-ad-rendering-role="story_message"]` (else `data-ad-preview`/`data-ad-comet-preview="message"`) — a shared post has two, sharer's note + original. Falls back to `article.inner_text()` when none is marked or it's ≤20 chars. The whole-article text dragged in the author header, Follow/timestamp chrome, reaction counts and comments; the header alone caused false `EXCLUDED_LOCATIONS` rejects (author "אפי עוזיאל" matched the excluded street עוזיאל). `_strip_comment_section` still runs on the result as a second line of defence. Unverified against live FB at commit time — confirm with a `--dry-run` that posts' text no longer starts with the author/"7h ·" lines.
- **Shared Marketplace card** (`_read_listing_cards()`, 2026-11-11): a post sharing a Marketplace listing shows the price only on the attached card — an `a[href*="/commerce/listing/"]` (or `/marketplace/item/`) link outside the body container, text `₪9,250 · <city> · <title>`; each card photo is its own text-less link. Its caption is appended to the body text, so the price pre-filter and the LLM see it. Verified live on `groups/1380680752778760/posts/2289910045189155` (now pre-filtered as 9,250 out of range, no LLM call). The button text `Message` comes along; harmless.
- **GraphQL capture, observational** (`graphql_capture.GraphqlPostCapture`, 2026-11-07): attached per group before `goto` (catches the first feed load) and always detached in `_scan_group_page`'s `finally` — sequential mode reuses one page, so a leaked listener would stack across groups. After the scroll it prints `GraphQL capture: N captured, M/K DOM posts matched (T with text), dates agree on A/B` — the evidence for later replacing relative-date parsing and comment stripping with the captured `creation_time`/`message.text`. Parser walks each `post_id` node's subtree, skipping `feedback`/`comment` keys and nested posts (a shared original is its own post_id). Payload shape unverified against live FB at commit time.
- 7-selector fallback chain for article extraction in `_scan_group_page` — FB DOM changes without warning (last resort: `div[aria-labelledby][aria-describedby]`, FB post containers carry both even when `role="article"` is absent)
- **Post-URL canonicalization** (`_canonical_post_url`, inside `extract_post_info`): FB serves the same group post as both `/groups/<gid>/posts/<pid>` and `/groups/<gid>/permalink/<pid>`, on www/m/web hosts — all normalized to `https://www.facebook.com/groups/<gid>/posts/<pid>/` (trailing slash kept, matches the shape already stored in DB/sheet) before any dedupe check, so a re-encountered post under a different URL shape can't cost a duplicate LLM call. Unknown URL shapes pass through unchanged.
- `chrome_profile/` directory locks when Chrome is running — kill zombie Chrome processes before rerun
- `MAX_CONCURRENT_GROUPS` (config.py) trades speed for detection risk — multiple simultaneous tabs from one FB account is a more bot-like pattern than sequential scanning
