## LLM Details

- **Primary**: an ordered model chain, `GEMINI_MODELS` in `config.py` (quality-first: `gemini-3.6-flash` → `gemini-3.5-flash` → `gemini-flash-latest` → `gemini-3.1-flash-lite`, verified callable against this key 2026-08-04), via `google-genai`, forced JSON via `response_mime_type="application/json"`. `gemini-2.0-flash` was retired 2026-06-01, and dated-snapshot names (`gemini-2.5-flash`, `gemini-2.5-flash-lite`) 404 for this key ("no longer available to new users") even though `client.models.list()` still lists them — only rolling `-latest`/named-tier aliases actually respond, and even those can 503 ("high demand") independently of each other, which is exactly what the chain is for. `core/llm.py`'s `_gemini_model_idx` (module-level, guarded by `_gemini_lock`) tracks the current position; `_advance_gemini_model()` moves to the next entry and resets `GEMINI_ERROR_COUNT`, setting `GEMINI_EXHAUSTED` only once the pointer runs past the last entry. A 404/NOT_FOUND or a *per-day* 429 (`_quota_kind()` reads `PerDay` from the error text) advances immediately (that model's dead for the run); a per-minute or unnamed 429 is first retried on the same model `GEMINI_RATE_LIMIT_RETRIES` times, sleeping Google's own `retryDelay` (`_retry_delay_s()`, capped at `GEMINI_RETRY_MAX_SLEEP_S`), and only advances if it keeps failing — a burst of per-minute 429s used to retire a healthy model for the whole run; any other error advances only after `GEMINI_MAX_CONSECUTIVE_ERRORS` in a row *on that model*. Per post, at most 2 models are tried before falling through to Ollama for that post — keeps one malformed post from walking (and burning the error budget of) the whole chain, while the global pointer still advances per the rules above so a genuinely dead model is learned run-wide.
- **Free chain extended** (2026-11-07, user wants to stay free): every model has its own daily free quota, so `GEMINI_MODELS` now continues `gemini-3.5-flash-lite` → `gemini-flash-lite-latest` → `gemini-3.1-flash-lite` → `gemma-4-26b-a4b-it` (~2s) → `gemma-4-31b-it` (~24s) before Ollama, all probed callable with `response_schema` that day (Gemma models' missing keys validate to None). `gemini-3.8-flash`/`3.7-flash` answered 429 on the free tier — not added until confirmed after a reset. `--eval` on the 8 fixtures with the top two models exhausted: chain 42/42 (100%), 4.8s/post; local `qwen2.5:7b` 38/42 (90%, misses mostly `is_agent`=None), 10.9s/post. The local model is `config.OLLAMA_MODEL`; compare candidates with `--eval --ollama-model <name>`.
- **Fallback**: `ollama.chat(model='qwen2.5:7b', format=ApartmentData.model_json_schema(), options={'temperature': 0, 'num_ctx': 4096}, keep_alive='10m')` — schema-constrained decoding, no manual JSON repair. Only reached once the entire `GEMINI_MODELS` chain is exhausted (`GEMINI_EXHAUSTED`), or for a single post that fails its up-to-2-models attempt. `_ensure_ollama_running()` (`core/llm.py`) auto-starts `ollama serve` the first time this path is actually needed and it's unreachable at `http://localhost:11434` — checked once per process (`_ollama_verified` flag), non-fatal if the `ollama` binary is missing.
- **Concurrency safety of the chain**: group threads × post workers share `_gemini_model_idx`, so `_advance_gemini_model(failed_model)` is a no-op unless `failed_model` is still the active entry (verified 2026-10-15: without this, one 429 burst made 4 concurrent threads each advance the pointer and skip the whole rest of the chain, sending ~90% of calls to Ollama); error counts from a model already moved past aren't charged to the next one. A transient 503/UNAVAILABLE is retried on the *same* model `GEMINI_UNAVAILABLE_RETRIES` times with `GEMINI_UNAVAILABLE_BACKOFF_S`-scaled sleeps before it counts as an error. A 429's message (first 300 chars) is logged so a per-minute limit can be told from a daily quota.
- **Model recorded per post + deterministic** (2026-11-07): `core.llm.last_model_used()` (thread-local — group threads × post workers run concurrently) returns the Gemini model name or `ollama:qwen2.5:7b` behind the current thread's last result; `_analysis_from_fields()` writes it to `posts.model_used` by default (was a fixed `gemini_or_ollama` on all 377 parsed posts, so models/fallback rate couldn't be compared). Gemini now runs at `temperature=0` like Ollama — extraction must parse the same post the same way every time.
- **No-amount pre-filter** (`_has_price_amount()` in `core/evaluate.py`, last gate in `_content_prefilter`): with `INCLUDE_PRICE_UNKNOWN=False`, a post with no 4-5 digit amount (separator/hyphen allowed — "שכ״ד-5900") and no price in words ("6.2 אלף", "אלפים", "6K"), phone numbers removed, is recorded `price_unknown` (reason `no_price_amount`) with no LLM call. Measured on 378 LLM-parsed posts: skips ~19% of calls, changes no added/duplicate/price-rejected verdict.
- **Global flag**: `GEMINI_EXHAUSTED` (module-level bool in `core/llm.py`) — true only once every entry in `GEMINI_MODELS` has failed
- **Validation**: both paths' raw output is validated against the `ApartmentData` Pydantic model in `analyze_post_with_llm()` — on failure, one retry (fresh LLM call), then `None` (verdict `parse_failed`)
- **Prompt**: `prompts.py` → strict JSON, keys: `rooms, price, arnona, vaad, shelter, parking, entry_date, floor, elevator, is_agent, address`. Post date is computed in Python from Facebook's relative timestamp (`relative_to_date`), not asked of the LLM. Assumes an English-locale FB UI: handles both short (`6h`, `1d`, `3w`) and long (`3 hrs`, `1 day`, `2 wks`) relative forms plus `Yesterday` and absolute dates (`July 9 at 5:50 PM`, via `_parse_absolute_fb_date`). An unrecognized format passes through unchanged (never crashes) and logs one `_safe_print` warning per run (`_unparsed_date_logged` flag) rather than degrading silently — if that warning starts appearing, the FB account's UI locale likely changed.
- **Text cap**: 3000 chars (prompt truncates the input text, not the instructions)
- **Comment-section stripping**: `article.inner_text()` also captures the comments thread below a post. `_strip_comment_section()` (`core/normalize.py`, right after the `BIDI_RE` strip) cuts the text at the first comment-section marker (`View more comments`, `View N repl`, `Write a comment`, etc.) — or, when FB renders a post's first comments inline with no such marker (435 of 7,845 stored posts, 2026-11-07), at the first comment-shaped block (`<name>` / `·` / `15m` / text / `Reply`, `_COMMENT_AGE_RE`) — before it's stored or analyzed, so a commenter's number/price can't contaminate the LLM's extraction of the listing itself. Trade-off: a price that exists *only* in a reply is lost — deliberate, since third-party comment numbers aren't reliable anyway.
- **Sale-listing pre-filter is price-based, not keyword-based**: many agent posts never say "למכירה" and just state a 7-digit price ("מחיר: 3,395,000 ₪"). The pre-filter in `_scan_group_page` matches a 7+-digit price (or "X מיליון") on its own — no monthly rental costs that much, so the word isn't required. The `[.,]\d{3}` separator requirement keeps it from matching phone numbers.
- **Test fixtures**: `tests/fixtures/test_posts/*.txt` — 8 fabricated Hebrew posts covering full/partial fields, agent vs. private, street vs. landmark vs. no address, an old-price distractor, and roommate/couple-flexibility edge cases; used to sanity-check both prompt variants against the Ollama path
